There is nothing wrong with closing a ticket.

That's what we're there to do.

The problem is when closing the ticket becomes the only measure of whether we've done a good job.

Sometimes restoring the service is the right outcome.

Sometimes there is another question worth asking.

## A ticket can be fixed and the problem can still exist

Imagine something breaks.

You investigate it, find the cause, apply a fix and the user is back up and running.

Good.

The ticket can be closed.

But what if the same thing happens next week?

Then again the week after?

At some point, the individual ticket isn't the interesting part anymore.

The pattern is.

I've become much more aware of that through working in support and studying service management.

A recurring issue can tell you something about the service around it.

It might be a configuration problem.

It might be a process problem.

It might be a documentation gap.

It might be something outside the service desk entirely.

You don't know until you look.

## The support queue can tell you a lot

You don't always need a complicated reporting system to notice patterns.

Sometimes you just recognise the same issue appearing again.

The same application.

The same type of access problem.

The same question from users.

The same workaround.

When I notice that, I try to ask what is behind it.

Not every repeat issue needs a major project.

Sometimes the answer is simply better documentation.

Sometimes it is making a process clearer.

Sometimes it is raising something with the team that owns the service.

But if you don't notice the pattern, you never get the chance to improve it.

## This is where service management started making more sense to me

One of the things I like about studying ITIL is that it gives structure to things I've already started noticing in support.

The individual incident matters.

But so does the service around it.

There is a difference between restoring something for one user and improving the way the service works for everyone.

That doesn't mean every support engineer needs to start redesigning services every time they close a ticket.

It just means the ticket can sometimes be useful information about something bigger.

## A simple example

Take documentation.

If three people ask the same question, you can answer three tickets.

Or you can ask whether the answer should be somewhere people can find it.

Neither approach is necessarily wrong.

But the second one might save time for the next person.

I've worked on documentation and knowledge articles for exactly this reason.

If the same information keeps being needed, having a useful reference makes sense.

The same applies to a process.

If someone has to ask how to complete something every time, perhaps the process isn't as clear as it could be.

## The important part is not overcomplicating it

I don't think every repeat ticket is evidence of a major underlying problem.

Sometimes things just happen.

Sometimes the same question comes up because someone is new.

Sometimes the fix is already known and the issue is simply unavoidable.

The point is to notice.

Then decide whether it is worth doing something about.

That is a much more useful approach than assuming every repeated ticket needs a huge improvement programme.

## What I'm trying to do differently

When I see a recurring issue, I try to think about what sits behind it.

Could documentation help?

Could the process be clearer?

Is there something the resolver team should know?

Is there a pattern worth raising?

Does this need further investigation?

Sometimes the answer is no.

Sometimes it is worth doing something.

The important thing is that the question gets asked.

## Closing the ticket is still important

I'm not against ticket closure.

A service desk still needs to restore service and keep work moving.

The point is that the ticket shouldn't always be the end of the thinking.

Sometimes the most useful thing you can do with an incident is close it.

Sometimes it's close it, learn from it and change something.

That distinction is one of the things that has made service management increasingly interesting to me.

A fixed ticket helps one person.

A useful improvement can help everyone who would have had the same problem next.
